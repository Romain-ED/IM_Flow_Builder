# Technical Design: Playable Video in the RCS Simulator

The implementation will add browser-native playback for authored RCS `video` messages without changing the existing message schema, scenario format, or transport payload. The locked stack is React 19, TypeScript, Vite 8, Tailwind CSS 4, Zod, Zustand, and Vitest with Testing Library. The selected playback primitive is `<video controls playsInline preload="metadata">`; it provides native play/pause/seek controls, keyboard operation, codec handling, and normal browser user-gesture policy without a custom player or simulator state transition. The current shared `VideoMessage` component will make an explicit channel decision: RCS uses the new player, while non-RCS channels retain the current thumbnail-button and simulator-toast behavior. This keeps the requested change scoped to RCS even though the renderer component is shared.

## Existing integration points and unchanged contracts

`src/schema/messages.ts` is authoritative for the existing `video` shape: `type: 'video'`, optional `url`, optional `thumbnailUrl`, optional `caption`, and optional `durationLabel`. No schema or authoring-format change is required. `ConversationEngine` already deep-interpolates complete message objects, so the Domino’s `campaignVideo` variable reaches the component as a normal `url`. `src/scenarios/dominos-rcs-video-campaign.yaml` already uses `/assets/dominos-rcs-video-campaign/gemini_generated_video_1c89463b.mp4`, and the file already exists below `public/assets/dominos-rcs-video-campaign/`. `src/scenarios/index.ts` already registers the scenario.

`MessageRenderer` will continue to pass `channel`, `interactive`, and `timestampLabel` to `VideoMessage`; `interactive` remains needed by the non-RCS legacy branch. The RCS branch will deliberately ignore `interactive`: native media controls are local browser controls and must remain available in read-only/presenter/shared-link views without invoking flow actions, Zustand mutations, toasts, or navigation. `ConversationView` and `MessageRenderer` retain their existing read-only and trailing-action gating for all other message types. No changes are needed to `src/schema/messages.ts`, `src/engine/ConversationEngine.ts`, `src/messages/MessageRenderer.tsx`, `src/components/phone/ConversationView.tsx`, or channel capability definitions.

## RCS rendering and interaction

`src/messages/VideoMessage.tsx` will remain the public component entry point and will split its render path by `channel === 'rcs'`. The RCS path will use `MessageShell` with the existing `chrome="card"`, preserve the current caption and duration presentation, and render a fixed `relative block h-48 w-full overflow-hidden` media region. A valid source will render a single native `<video>` element with `controls`, `playsInline`, `preload="metadata"`, `src={resolvedSource}`, and `poster={resolvedPoster}` only when the optional thumbnail passes validation. It will not add `autoPlay`, a simulator play button, a toast, an `onClick` flow handler, or custom controls. The native controls provide play, pause, seek where supported, volume, and browser-standard keyboard access.

The component will use `useId()` for per-message `captionId` and `durationId`. The video will have `aria-label={caption?.trim() || 'Video'}` and `aria-describedby` referencing the generated caption and duration IDs when those values are non-empty. The existing `FormattedText` rendering remains in a caption paragraph with the generated caption ID. The authored `durationLabel` remains visibly overlaid in the media region and is also exposed through its generated ID. Empty optional metadata is omitted rather than rendered as empty accessible references.

RCS local state will contain only a `mediaError` flag. A native `error` event sets that flag and replaces the video with the local fallback; it does not throw, log an expected content failure, call the simulator store, or affect the conversation engine. An effect keyed by the resolved source clears the flag when a later message/source value becomes valid, allowing recovery after a source change. Missing or invalid input selects the fallback before a video element is created. Poster failure is independent: the browser may still play a valid source, and a failed fallback thumbnail is handled by the existing `ImageWithFallback` component.

The fallback will occupy the same `h-48 w-full` region to avoid layout shift, use `role="status"` and `aria-label="Video unavailable"`, and visibly state `Video unavailable`. If a validated thumbnail exists, it will render as a background/foreground image through `ImageWithFallback` with the authored caption as its alternative context; the explanatory unavailable text remains visible above or alongside it. The caption and duration remain below/within the card and retain their accessible IDs. Thus a missing, malformed, unreachable, unsupported, or load-failing source produces a stable readable per-message state while the rest of the conversation remains usable.

The non-RCS path will preserve the current implementation’s thumbnail image, play-preview button, `interactive` disabled behavior, and `useSimulatorStore().showToast('Video playback is not available in this simulator')`. It will not receive the native RCS player or change its side effects. The wrapper can place the current implementation in a private legacy subcomponent so the RCS subtree does not subscribe to or mutate the simulator store at all. This is the explicit boundary that prevents a shared renderer change from broadening video playback to WhatsApp or future channels.

## URL validation and base-path ownership

A new `src/utils/mediaUrl.ts` will define the client media contract. It will export two functions with distinct ownership:

```ts
export function validatedMediaSource(raw: string | undefined): string | undefined
export function mediaUrl(raw: string | undefined): string | undefined
```

`validatedMediaSource` trims the input, rejects empty values, ASCII control characters, DEL, protocol-relative `//` values, non-root relative values such as `video.mp4`, and unsupported schemes. It accepts a root-authored path beginning with `/` and absolute `http:` or `https:` URLs; absolute values are returned in URL-normalized form. `mediaUrl` calls that validator and, only for a root-authored path, applies the existing `assetUrl()` function exactly once. Absolute HTTP(S) values remain unchanged. No network request, extension check, or codec check occurs in this helper because remote URLs may use query strings and browser support owns decoding.

The single-resolution rule is important for non-root Vite deployments. `mediaUrl(message.url)` is used for the native video `src` and `poster`, because those DOM attributes do not otherwise call `assetUrl`. `validatedMediaSource(message.thumbnailUrl)`—the raw, validated value, not the result of `mediaUrl()`—is passed to `ImageWithFallback` for the fallback image. `ImageWithFallback` is already the owner of the one `assetUrl(src)` call for images. Consequently `/assets/poster.jpg` becomes `/simulator/assets/poster.jpg` exactly once when `BASE_URL` is `/simulator/`, never `/simulator/simulator/assets/poster.jpg`. Absolute thumbnail URLs pass through unchanged in both paths. The utility and component tests will assert this ownership rule explicitly.

The message schema continues to permit an optional/missing video URL because the normal simulator must show a graceful fallback rather than reject the entire conversation. The schema owns field types; `mediaUrl` owns client URL acceptance and Vite-base joining; `VideoMessage` owns browser load state; and the browser owns actual media decoding. These layers ensure malformed user-authored content is recoverable locally and never becomes an uncaught React error.

## Presenter/live projection and server boundary

The ordinary simulator path needs no additional scenario data. The read-only Live RCS projection must preserve `thumbnailUrl` and `durationLabel` for the simulator presentation, while the provider payload must continue to contain only the RCS-supported video URL and caption.

In `server/liveDemo.js`, `collectContent()` will add `thumbnailUrl` and `durationLabel` to the provider-neutral video object. Both media URLs will be resolved through a stricter `resolveMediaUrl()` contract: trim and reject empty/control-character values; accept root-authored paths only when `publicBaseUrl` is present; reject protocol-relative and non-HTTP(S) schemes; resolve root paths against `publicBaseUrl`; and allow HTTPS or HTTP only for `localhost`/`127.0.0.1` development. A video source is required for live delivery. If its URL is missing, malformed, protocol-relative, `javascript:`, `data:`, another unsupported scheme, or an insecure non-local URL, `collectContent()` throws a bounded content-validation error before `enterNode()` calls `gateway.send()`. The live session follows its existing error path (status `error`, safe `delivery_failed` diagnostic, and the caller receives the validation error); no invalid video is sent to Vonage. An invalid optional thumbnail is dropped, not fatal, because it is presentation metadata and does not prevent provider delivery. This server rule is defense in depth for the already-stricter `preflightLiveRcsFlow()` path.

`presenterUrl()` in `server/liveDemo.js` will also enforce the same allowed HTTP(S)/localhost scheme after parsing, in addition to its existing credential removal, sensitive-query-key removal, and 1,000-character bound. It returns an empty value for malformed or unsupported input. `liveMessageFromContent()` will include `thumbnailUrl` only when `presenterUrl(content.thumbnailUrl)` succeeds and will include `durationLabel` only when `boundedText(content.durationLabel, 64)` is non-empty. The validated source is projected with `presenterUrl(content.url)` and the caption continues through `presenterText()`. Because `collectContent()` enforces the source invariant before gateway delivery, an empty presenter source is a defensive projection failure rather than a normal path; it must not be substituted with an unsafe URL.

`src/live/liveSessionProjection.ts` will extend the internal video snapshot schema with optional `thumbnailUrl: z.string().max(1000)` and `durationLabel: z.string().max(64)`. `mapMessage()` will copy non-empty values into the existing `videoMessageSchema` shape. A wrong-typed or over-limit presenter field causes that timeline item to be skipped and increments `projectionWarnings`, matching existing projection behavior; it does not crash or invalidate unrelated timeline entries. A missing URL remains a valid projected message for the browser fallback when it comes from a snapshot that is otherwise valid, even though the normal live-server delivery path rejects it before sending.

`server/vonageRcs.js` will not change. `toVonageRcsMessage()` will continue serializing `video.url` and optional `video.caption` only; presenter-only poster and duration fields are never sent to the provider. The exact transport shape will be protected by a regression test containing all fields and asserting that the output excludes `thumbnailUrl` and `durationLabel`.

## Asset, styling, and build integration

No new media service, upload path, transcoding, CDN, or dependency is required. Existing Tailwind classes in `VideoMessage.tsx` provide the focused player/fallback styling; `src/index.css` and general message styling remain unchanged. `vite.config.ts` remains unchanged: Vite copies `public/assets/dominos-rcs-video-campaign/gemini_generated_video_1c89463b.mp4` into the build output as a public file, while the current Workbox glob intentionally does not precache MP4. Offline video playback is not required.

The built-in Domino’s scenario and asset are treated as data invariants, not rewritten. A scenario test will parse `dominos-rcs-video-campaign`, assert that `campaign_video` contains the exact required public MP4 path, and retain the existing Live RCS preflight check. The build check will assert that the generated output contains `dist/assets/dominos-rcs-video-campaign/gemini_generated_video_1c89463b.mp4`; a base-path build will additionally verify the browser URL convention `/simulator/assets/dominos-rcs-video-campaign/gemini_generated_video_1c89463b.mp4`.

## Error handling, invariants, and testability

For client URL validation, empty/invalid values are recoverable input failures: `validatedMediaSource()`/`mediaUrl()` return `undefined`, and the RCS component renders the local fallback without logging or throwing. For a valid URL whose resource is missing, unreachable, unsupported, or rejected by the browser, the native `error` event is recoverable at the message boundary and swaps only that message to the fallback. The caller sees a readable “Video unavailable” state; no store action, flow transition, toast, or uncaught exception occurs. A valid video with a missing or failed poster remains playable, and a failed fallback image is handled by `ImageWithFallback`.

For live server URL resolution, a missing or unsafe source is a fatal validation error for that live delivery operation because an RCS provider cannot accept a playable video without a safe URL. Validation occurs before `gateway.send()`; the caller receives the existing service error, the session enters the existing safe error/diagnostic path, and the provider receives nothing. An invalid optional thumbnail is recoverable and omitted. Presenter parsing is defensive and returns no URL for unsupported schemes; the collection invariant prevents that state from reaching the provider. Projection schema failures are recoverable per timeline item and counted in `projectionWarnings`.

The significant ownership invariants are: only RCS enters native playback; only `mediaUrl()` resolves a native video source/poster; only raw validated thumbnail values enter `ImageWithFallback`; only `VideoMessage` owns browser media state; native controls never call flow handlers; only safe live HTTP(S) URLs reach `gateway.send()`; projected messages remain valid against `messageSchema`; and provider serialization never includes presenter-only metadata. Unit tests cover pure URL validation and projection mapping. React/Testing Library tests cover DOM attributes, fallback transitions, accessibility associations, and channel isolation. Server tests cover pre-send validation and exact provider payloads. Build and runtime checks cover public asset delivery and actual browser playback.

## Validation and runtime smoke test

The implementation will run `npm test`, `npm run lint`, and `npm run build`. It will also run the focused media, component, projection, server, transport, and scenario tests directly while iterating. A second build with `VITE_BASE_PATH=/simulator/` will verify that the MP4 remains in the generated public asset tree and that rendered source/poster URLs have exactly one `/simulator/` prefix.

When browser automation is available, the built or previewed app will be opened on the Domino’s RCS scenario. The smoke test will inspect the video element for native controls, the configured resolved source, caption, and duration; interact with the native play control; and confirm playback begins or advances according to browser media policy. It will request the exact root URL `/assets/dominos-rcs-video-campaign/gemini_generated_video_1c89463b.mp4` and the base-prefixed equivalent, checking a successful MP4 response and normal media byte/range loading. It will also exercise a missing/error source fallback and verify neighboring text, image, rich-card, and carousel rendering. No secrets, unrelated infrastructure, or git history will be modified, and no commit will be created.

## Responses to design-review findings

1. **HIGH — Poster and fallback URLs double-applied the Vite base path: addressed.** The revised design assigns one resolver per DOM path. Native `video.src`/`poster` use the resolved result of `mediaUrl()`. The existing `ImageWithFallback` receives only `validatedMediaSource(thumbnailUrl)`, the raw validated value, so its internal `assetUrl()` call is the sole base-path join. The component and utility tests explicitly cover `BASE_URL=/simulator/` and assert `/simulator/assets/...` with no duplicated prefix.

2. **MEDIUM — Shared renderer broadened playback outside RCS: addressed.** `VideoMessage` now has an explicit `channel === 'rcs'` native-player branch. The non-RCS branch preserves the existing thumbnail preview, `interactive` gating, and unavailable-playback toast. `MessageRenderer` continues passing the existing prop because the legacy branch needs it, and a regression test covers non-RCS behavior.

3. **MEDIUM — Live server accepted unsafe URL schemes: addressed.** `resolveMediaUrl()` now rejects unsupported, protocol-relative, malformed, and insecure external sources before `gateway.send()`, allowing HTTPS and localhost HTTP only. `presenterUrl()` applies the same scheme check as defense in depth. Server tests cover `javascript:`, `data:`, protocol-relative, malformed, valid absolute, and valid root-relative inputs and assert that invalid content is never delivered.
