# Technical Design: Android RCS Conversation and Business Profile Screenshot Match

The implementation will stay within the existing React 19 + TypeScript + Vite + Tailwind CSS 4 + Zustand + Zod + Lucide stack. It will update the built-in Domino/RCS demo fixture and the existing RCS renderer, message components, composer, and business-profile overlay; it will not add a package, backend, route, persistence layer, or native screen. The RCS conversation will use the existing engine and action dispatch path, while a validated nested RCS profile model will select a dedicated profile layout without changing generic WhatsApp or generic profile behavior. Existing pizza images will be reused from `public/assets/dominos-singapore-rcs-demo/`; the small Vonage/RCS banner marks will be CSS/Lucide primitives because no suitable Vonage assets are present.

## Flow and data model

Extend `src/schema/flow.ts` with an optional `rcsProfile` field on `brandDefinitionSchema`. Keep ordinary `BrandDefinition` fields compatible with existing scenarios, and define a separate nested schema for the screenshot-only RCS profile. The nested model should contain the rendered display name (`Romain RCS Demo Agent`), secondary label (`Romain demo`), brand label (`Vonage`), phone (`9750 2284`), website display label and URL (`www.vonage.com` plus an HTTPS URL), email, image count (`44`), exactly three profile image URLs, and optional HTTPS policy/terms URLs. It may also contain an avatar URL, but the target avatar will use the shared CSS RCS mark unless an existing suitable asset is supplied.

Profile media and outbound URLs must use a shared safe URL schema: permit app-relative paths beginning with a single `/` and HTTPS URLs, reject protocol-relative URLs, `javascript:`, `data:`, `blob:`, whitespace-containing values, and empty strings. Image URLs are bounded strings; text fields have practical maximum lengths; email uses the existing Zod email validator; phone is a non-empty bounded string. A profile that selects the dedicated layout must have `imageUrls` with at least three entries, and the fixture will provide exactly three. Thus an `rcsProfile` with an empty image list is invalid rather than ambiguously rendering an empty dedicated Images row. A brand without `rcsProfile` continues to use the current generic profile layout.

The persistence boundary must no longer trust `StoredScenario.configuredBrand` merely because it was parsed from JSON. In `src/store/persistence.ts`, type the stored override as unknown-compatible data at runtime and add an editable override schema containing only the ordinary brand-editor fields (`name`, `shortName`, `avatar`, `logo`, `verified`, `description`, `website`, `supportPhone`, and `email`); it must not accept or replace nested `rcsProfile`. In `src/store/simulatorStore.ts`, add a helper such as `resolveConfiguredBrand(flow.brand, brandOverride)` that first validates the flow brand, safely parses the persisted editable override, and merges only valid editable fields over the validated base brand. The merge must always retain `flow.brand.rcsProfile`. An invalid, stale, or unsafe override is recoverable: discard it, use the validated flow brand, and continue loading; do not render the invalid value and do not throw. Use this helper in `initialize()`/`loadFlow()` and also validate patches in `updateConfiguredBrand()` before persisting. Persist the resulting safe brand so future loads cannot reintroduce the stale nested object. Existing avatar data URLs created by the brand editor remain supported only for the existing top-level avatar field; dedicated profile media uses the stricter URL schema.

Update `src/scenarios/dominos-singapore-rcs-demo.yaml` so the RCS demo fixture supplies the target identity: brand name/short name `Romain RCS Demo Agent`, description `Romain demo`, contact values `9750 2284`, `https://www.vonage.com`, and `romain.edin@vonage.com`, plus the nested `rcsProfile` values and three direct app-relative pizza image paths. Reuse the existing `imgi_3...`, `imgi_5...`, and `imgi_13...` pizza assets (or the corresponding existing paths if the asset names are adjusted during implementation). Do not introduce new art merely for the banner; render its R mark and chat bubbles as local CSS/Lucide shapes.

Make the fixture’s `start` equal `promotions`, but also make `promotions` itself the deterministic screenshot target rather than relying on start-node selection or a playback timing window. Its message sequence will contain only the carousel followed by the `More options:` text and its attached reply choices; remove the current lengthy “Ready to order...” messages from this node and retain them unchanged in the existing `post_promo_nav` node reachable from a More-options choice. Keep the first two cards and their existing action `next`/`set` semantics, with the first card text exactly `Everyday Value — 1 Regular Pizza`, `1 Regular Pizza for just $5.99! Choose from our classic range. Perfect for a solo meal. 🍕`, `Order for $5.99`, and `See All Deals`; ensure the second card title/body begins with the `$9.99` offer. Set the screenshot node’s per-message typing/delay values to zero (or use the fixture defaults consistently) so the settled state is deterministic, while retaining normal action-driven flow transitions. The compact node must fit the phone conversation viewport at 360 CSS pixels: no extra greeting or post-carousel paragraph may be added to it. Tests will assert the exact node order, start node, card text, and the presence of `More options:`; a narrow rendered check will assert that both the first card and More-options element are visible after playback has settled.

## RCS renderer, header, theme, and conversation

Modify `src/channels/rcs/RcsRenderer.tsx`, `src/channels/rcs/RcsHeader.tsx`, and `src/channels/theme.ts`. The RCS renderer should use a pale lavender Android Messages-like conversation surface and pass the existing profile click callback through unchanged. The header should have the pale lavender treatment, a back arrow, a green rounded-square RCS agent avatar, the exact title `Romain RCS Demo Agent`, and a right-side overflow button. For a target nested profile, use a small reusable CSS/Lucide RCS avatar/mark component rather than the existing circular generic Avatar; retain the existing Avatar fallback for other RCS brands. The title should come from the validated nested profile display name when present and otherwise preserve current brand-name behavior. Keep the title button as the profile-opening integration point.

The header back button has no parent route in the phone simulator, so it must not invent navigation: keep it keyboard-focusable and have it call the existing simulator toast path with a truthful “Back navigation is not available in this demo” message (or use the established store back operation only if the surrounding phone navigation contract is confirmed during implementation). The overflow button similarly calls the existing `showToast` action with a truthful unavailable-in-demo message. These controls must have meaningful `aria-label` values. Existing non-RCS header behavior is untouched.

Use the RCS theme’s pale lavender `screenBg`, subdued Android-like borders, and purple/blue accent values in place of the current cool gray presentation. Keep the existing theme-driven message/action semantics. Add a narrow RCS-only visual treatment for the authored text exactly equal to `More options:`: render it as a compact rounded lavender chip in the message area, while preserving any attached choices as keyboard-accessible existing reply controls. This can be implemented by extending `MessageShell` with a chip chrome or by a dedicated small renderer path in `TextMessage`; it must not affect identical text in WhatsApp or other channels. The text remains a real flow message so attachment validation and action dispatch are unchanged.

In `src/messages/Carousel.tsx`, retain the existing `ImageWithFallback` and `ActionButton` integration, but make RCS cards visually match the reference: larger rounded cards, compact image area, stable title/body/button spacing, and a responsive card width that is approximately the content width minus 56 pixels with a 260-pixel maximum. This intentionally exposes part of the second card at a narrow phone width. The scroller must have `min-w-0`, local `overflow-x-auto`, snap behavior, and no page-level horizontal overflow. Calculate desktop arrow movement from the actual card/scroller width or use the same bounded card width; do not keep a hard-coded offset that skips cards at narrower widths. Pointer/touch scrolling remains native. Card buttons continue to call `ActionButton` and then `useSimulatorStore.handleAction`, so `reply`, external-action, and set-variable behavior remain unchanged. Do not add a full-screen image viewer, image provider, gallery state, or overlay: the requirements only need carousel scrolling and reusable image presentation.

`src/components/phone/ConversationView.tsx` may retain its existing scroll-to-bottom effect because the target node is deliberately compact and settled playback shows the whole target composition. If implementation measurements show the compact fixture still exceeds the phone viewport, make the scroll behavior deterministic for the initial RCS promotions node (for example, preserve a named initial-anchor position until the user scrolls) and cover that behavior in a rendered test; do not solve it by relying on a timing interval. The preferred implementation is the compact flow because it avoids changing scrolling behavior for every scenario.

## Composer

Modify `src/components/phone/Composer.tsx` without changing store submission APIs. Preserve the current live-session, terminal, and error branches first. Preserve the current structured-input form whenever `inputMessage` exists, regardless of channel; this is the explicit precedence rule. Only when `channel === 'rcs' && !inputMessage && !liveSessionActive && !ended && !errored` should the screenshot composer render.

The RCS free-text form will be a rounded lavender/white Android-like control with a plus button, an input whose exact placeholder is `RCS message`, emoji and image/media icon buttons, and a purple rounded voice/action button. The input still submits through `handleFreeText`, so keyword routes and normal free-text behavior are preserved. The plus, emoji, and media buttons are local demo controls with accessible labels and a truthful existing toast rather than fake integrations; they must not submit or mutate flow state. The purple action button submits the text when non-empty and otherwise remains a harmless disabled/guarded action. Keep the generic composer for WhatsApp and any other non-RCS free-text state. Add tests covering an RCS free-text render, RCS structured input precedence, and WhatsApp structured input precedence.

## Dedicated RCS business profile

Keep `src/components/phone/BusinessProfileView.tsx` as the channel-neutral entry point and add `src/components/phone/RcsBusinessProfileView.tsx` for the dedicated branch. When `channel === 'rcs'` and the validated `brand.rcsProfile` exists, render the new component; otherwise render the current generic profile. Since the schema requires at least three safe image URLs, the branch has no empty-image ambiguity. `PhoneScreen.tsx` continues to pass the configured brand and existing open/close state; no new route or global modal state is required.

The dedicated component is an absolute, full-phone overlay with a pale lavender background and a compact Android-like top bar. The top bar has a working back button that calls `onClose`, the `Info & options` title, and a keyboard-focusable `More profile options` overflow button. The overflow action is deliberately local and truthful: it calls `showToast('More profile options are not available in this demo.')`; it does not open an undefined menu or perform a real account operation. The toast is rendered by the existing `Toast` sibling in `PhoneScreen`.

Build the green banner from CSS gradients/shapes and Lucide `MessageCircle`/bubble primitives, with visible text `Romain`, `RCS Agent Demo`, and `Vonage`, an outlined `R` mark, and the small chat-bubble marks from the reference. Use the same green CSS RCS avatar component as the header, positioned overlapping the banner. Beneath it, center `Romain RCS Demo Agent` and `Romain demo`. Use four equally sized pale-blue action controls labeled `Call`, `Website`, `Email`, and `Search`; Call/Website/Email use the validated `tel:`, HTTPS, and `mailto:` behaviors already used by the generic profile, while Search is a local button that reports it is unavailable in the demo. Do not claim to implement real integrations.

Render an Images row with the literal count `44`, a right chevron, and exactly the first three validated pizza URLs as non-interactive thumbnails using `ImageWithFallback`. There is no full-screen viewer. Render separate accessible detail rows for phone `9750 2284`, website `www.vonage.com`, and email `romain.edin@vonage.com`, followed by rows labeled `View Privacy Policy`, `View Terms of Service`, `Notifications`, `Chat theme`, and `Archive`. Policy/terms use validated HTTPS links when fixture URLs exist; settings rows are local controls that show a truthful unavailable toast, not fake settings changes. Render a visually distinct red `Block and report spam` local action with a truthful toast, and the bottom RCS encryption disclaimer with a `Learn more` local action/toast. Preserve vertical scrolling inside the profile and ensure thumbnails, labels, and controls do not create horizontal page overflow.

Failure behavior is explicit: an absent optional profile uses the existing generic screen; malformed flow profile data is rejected by flow validation and the app’s existing scenario fallback path remains responsible for reporting it; stale persisted overrides are discarded in `resolveConfiguredBrand`; an image load error is recoverable through existing `ImageWithFallback` fallback UI; a failed external navigation is browser-owned and not converted into a simulator success; local profile-only controls never throw and report their unavailable state through the existing non-fatal toast. No profile control mutates the scenario or invokes a backend.

## Error handling and invariant ownership

Zod owns all flow/profile shape, field-length, email, and safe-URL invariants at the flow-validation boundary because authored YAML/JSON and shared scenarios are untrusted external input. The persistence resolver owns stale/unsafe localStorage data and returns a validated base brand on failure; localStorage parse/read/write failures remain non-fatal under the existing persistence policy. The simulator store owns action guards (`liveSessionActive`, missing flow/current node, terminal/error state), and all existing card actions continue to return through those guards. Components own only presentation-level fallback: missing/broken media goes through `ImageWithFallback`, missing optional profile selects the generic layout, and icon-only buttons have labels. Browser-owned `tel:`, `mailto:`, and HTTPS navigation is not simulated as successful application behavior. Local controls that have no implementation are recoverable and use a toast; they never throw, alter flow state, or claim completion. The dedicated branch’s `imageUrls.length >= 3` invariant is schema-owned so the renderer can safely render its three-thumbnail contract.

## Testability and verification

Unit tests will parse the target YAML and assert that `start` is `promotions`, the compact node order is carousel then `More options:`, the first card’s exact title/body/actions are present in order, and the second card contains the `$9.99` offer. Schema/store tests will seed localStorage with (a) an old override missing `rcsProfile`, (b) an override containing `javascript:`/`data:` nested profile URLs, and (c) a valid ordinary name/avatar edit; they will assert that the validated flow profile is retained, unsafe nested values never reach state/rendered `src`/`href`, and valid editable fields still apply. Add a rejection test for a present `rcsProfile` with zero images and a generic-layout test for a brand without `rcsProfile`.

Component tests will verify the header labels/accessible controls, dedicated profile labels, three thumbnails, image count, overflow toast, back callback, block/report and Learn-more controls, and the RCS-only More-options chip. Composer tests will verify the exact `RCS message` placeholder and icon labels, that an active structured input wins over the RCS branch in both RCS and WhatsApp, and that free-text submission still calls the existing store handler. Carousel tests will verify local horizontal overflow/snap classes, partial-card bounded width, exact card copy, action labels, and that action clicks reach the existing handler.

Run `npm test`, `npm run lint`, and `npm run build`; fix all type/lint/test failures before delivery. Because `package.json` contains no browser or screenshot dependency, perform the visual verification with the repository’s existing dev/preview app (no dependency addition): render the phone at a narrow Android-like 360 CSS-pixel viewport, wait until the deterministic promotions node settles, confirm the first card, partial second card beginning `$9.99`, `More options:` chip, and composer are simultaneously visible, then open the profile and confirm its banner, four actions, image row, details, settings, red action, disclaimer, and internal scrolling. Inspect the browser console and page scroll width for runtime errors or page-level horizontal overflow. If the repository later exposes an existing browser harness, use it; otherwise record this manual narrow-viewport execution as the visual check rather than claiming source inspection proves fidelity.

## Responses to design review findings

1. **Persisted configuredBrand overrides bypass `rcsProfile` validation — addressed.** The design adds a persistence-boundary editable override schema, rejects/strips nested profile overrides, validates and merges overrides onto the validated `flow.brand`, and adds stale/unsafe-localStorage regression tests. The flow’s nested profile is never replaced by a stored object.
2. **`start: promotions` does not guarantee the required initial visible state — addressed.** The target fixture’s promotions node is explicitly compact and ordered as carousel then `More options:`; lengthy follow-up messages move to `post_promo_nav`, and tests plus a narrow rendered check assert both elements after settled playback. The design does not rely on start selection or a timing window alone.
3. **RCS composer precedence over structured inputs is ambiguous — addressed.** The branch predicate is explicitly `channel === 'rcs' && !inputMessage && !liveSessionActive && !ended && !errored`, with live/terminal/error and structured-input branches taking precedence. Tests cover structured inputs in both channels.
4. **Full-screen image viewer is out of scope — addressed.** The design removes the viewer/provider/overlay and retains `ImageWithFallback` thumbnails/media only.
5. **Retained image viewer lacks filtered-index and focus contracts — addressed by removal.** No viewer, selected index, focus restoration, Escape handling, or related state will be implemented.
6. **Dedicated profile overflow behavior is unspecified — addressed.** The dedicated overflow is a labeled local button that invokes the existing toast with a truthful unavailable message; a component test covers it.
7. **Empty `imageUrls` conflicts with the dedicated branch — addressed.** A dedicated profile requires at least three safe image URLs; absent `rcsProfile` is the generic branch, while an explicitly present empty-image profile fails schema validation. Tests cover both valid dedicated and generic cases.
