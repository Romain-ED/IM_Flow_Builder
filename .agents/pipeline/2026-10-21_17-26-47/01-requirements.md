# Requirements: V Bank RCS Multifinance Journey

## Summary
Add a discoverable built-in RCS scenario titled **“V Bank: From just curious to first repayment”**. It is a fictional Indonesian multifinance journey following fictional customer Nadia from borrowing discovery through indicative eligibility, application handoffs, approval, signing/disbursement, and first repayment. The scenario must use the repository’s YAML state-machine format and only standard RCS capabilities supported by the project. Rates, amounts, dates, reference numbers, sender identity, and “OJK Supervised” branding are illustrative demo content only; no real person, lender, regulatory status, or financial offer may be implied.

Assumptions: the existing `open_url` action is the project’s representation of a secure browser handoff; RCS does not provide native document upload, liveness, contract-signing, or payment-entry screens, so those steps are represented by URL actions plus return/confirmation reply nodes. Existing repository media may be reused as visibly generic placeholders until replacement artwork is supplied.

## Functional Requirements
- Create an authored-channel RCS scenario with a unique kebab-case ID, V Bank fictional brand metadata, verified-sender styling only as demo presentation, and explicit illustrative/compliance disclosures in the journey. Register it using the existing built-in scenario registry so it appears in scenario discovery and can be loaded by ID.
- Start with a discovery carousel containing exactly three borrowing options: Personal Loan, Car Loan, and Home Mortgage. Each card must include a reused repository image placeholder, fictional indicative rate copy, concise product description, and RCS-supported actions for eligibility and details. Details must preserve the illustrative/rate-basis disclosure; eligibility must enter the personal-loan qualification path.
- Gate qualification behind consent. Present consent wording that says the assessment is initial/indicative, explains use of answers and existing account information, and does not imply approval. Include an agree/continue branch and a decline/not-now branch that ends or returns safely without collecting sensitive data.
- Ask the three qualification questions using suggested replies: monthly income, employment status, and existing monthly loan/credit-card repayments. Store each selection in scenario state and provide a coherent, reachable branch for each answer group. After all three answers, show an indicative result such as up to Rp 150,000,000 with a prominent “initial eligibility only; final approval follows documents and credit checks” disclaimer. Do not claim that the answers perform a real credit decision.
- Offer amount/term selection through an `open_url` secure browser handoff. Represent return-to-chat progression with supported reply actions and state, not a native form or invented RCS UI. Include fictional selected amount/term, estimated repayment, and an illustrative disclosure before application continuation.
- Show an application document checklist rich card with two fictional requirements (KTP identity card and latest payslip), status progression from 0 of 2 to each received and complete. Each upload operation must be an `open_url` handoff to a secure fictional/app-relative HTTPS destination and return through a reply branch; no native upload control or real document/PII is required.
- Provide a liveness/identity verification step with a secure browser `open_url` handoff, a return/verification branch, and a clear message that the flow is a demo and does not actually verify identity. Continue to review only after the represented verification step.
- Present an approval rich card containing fictional final rate, approved principal, monthly instalment, fees, total repayment, and a fictional reference. Distinguish final illustrative approval content from the earlier indicative result and retain disclosures. Provide a secure contract review/signing `open_url` handoff, an authentication/signing return branch, a contract-signed confirmation, and a disbursement confirmation into the fictional V Bank account.
- Model servicing after disbursement: send a first-repayment reminder with fictional amount and due date, offer payment methods through suggested replies including BCA, Mandiri, BRI, and Alfamart, and return method-specific virtual-account/payment instructions. Include an “I’ve Already Paid” reply action, a checking-payment state, payment-received confirmation with amount, and a receipt action represented by an `open_url` handoff. Include a safe path for cancellation, later payment, or help where useful.
- Use realistic state variables and transitions supported by the current schema (`set`, `condition`, `next`, and action `next`/`set`) so selected product, consent, qualification answers, application progress, handoff returns, payment method, and payment status are reflected in later messages. Every node must have a valid outcome and every reference must resolve.
- Use only RCS-supported project primitives: `text`, `image`/card media, `rich_card`, `carousel`, `suggested_replies`, `suggested_actions`, and `open_url`/reply actions. Keep suggestion labels within the project’s RCS limits; use 2–10 carousel cards, no more than four card-owned actions per card, and no more than 11 standalone suggestions. Reuse existing repository image paths only; do not fetch, generate, or add assets or dependencies.

## Non-Functional Requirements
- Preserve platform honesty: do not use simulator-only `input`, `list`, `system_action`, payment-request, OTP, calendar, or other invented native UI. Browser handoffs must use app-relative or HTTPS URLs acceptable to the schema and must not contain secrets or real customer data.
- Keep all displayed financial and compliance copy fictional, Indonesian-contextual, and explicitly illustrative. “OJK Supervised” may appear only as fictional branded demo artwork/placeholder wording and must not be presented as a real certification or factual claim. Use fictional Nadia data and no real PII.
- Follow existing scenario formatting and registration conventions. The implementation must not modify unrelated scenarios, runtime behavior, dependencies, deployment configuration, or external services.
- The scenario must pass parsing, schema validation, authored-channel RCS compliance, officially-supported-message-type checks, and Live RCS preflight with its placeholder media and handoff URLs. Validation should be covered by the repository’s existing test commands plus focused scenario loading/flow checks.

## Acceptance Criteria
1. A new built-in scenario is importable from `src/scenarios/index.ts`, discoverable by its unique ID, opens with the V Bank name, and has `metadata.channel: rcs`.
2. The main path can be exercised from discovery carousel → consent → all three suggested-reply questions → indicative result → browser handoff return → document checklist/upload returns → liveness return → approval → contract return → disbursement → repayment reminder → payment method → virtual-account instructions → “I’ve Already Paid” → payment received → receipt URL.
3. Discovery visibly contains Personal Loan, Car Loan, and Home Mortgage cards with reused existing image paths and no newly created/fetched assets; the final report identifies every reused placeholder path.
4. Consent, indicative eligibility, fictional rates/amounts, approval/payment values, and “OJK Supervised” presentation include explicit illustrative/demo disclosures; no real PII or unsupported factual claim appears.
5. Qualification state records income, employment, and repayment selections; branches are reachable, and refusal/cancel/later/help outcomes do not dead-end unexpectedly.
6. Every interactive message uses a valid preceding content message, every carousel has 2–10 cards, every card has at most four actions, every standalone suggestion group has at most 11 chips, and all labels/URLs satisfy schema and RCS limits.
7. Repository validation passes without dependency changes: scenario tests, RCS compliance/preflight checks, lint/type/build checks as applicable, plus a targeted runtime or DOM check proving scenario discovery and the main flow load successfully. No commit or push is created.

## Out of Scope
- Real lending, credit scoring, eligibility decisions, regulatory validation, KYC/liveness verification, document upload, contract execution, disbursement, payment processing, banking integrations, or receipt generation.
- Native RCS UI beyond official content/suggestion/card capabilities, including embedded forms, file pickers, camera/liveness screens, signature widgets, virtual-account payment widgets, or payment requests.
- New artwork, external asset downloads, new packages, live provider configuration, changes to `server/liveDemo.js`, or production/deployment changes unless existing validation exposes a necessary compatibility issue.
