# Technical Design: Reliable Live Demo, RCS Realism, and Accessible Selectors

## Overview

Implement this as a progressive enhancement of the existing React 19 + TypeScript + Zustand + Zod + Tailwind/Vite application, with no new dependencies. Keep `validateFlowWithChannelCompliance` as the scenario-load/editor gate and extend `preflightLiveRcsFlow` as the live/payload gate. Persist only same-browser navigation state, keep real-provider transport boundaries unchanged, and make the visual preview usable even when a configuration is warning-level invalid. The primary authoring surface remains the existing YAML/JSON Scenario Editor and imported/built-in flow schema; no second form editor is introduced.

## State, validation, and payload model

Extend `src/schema/messages.ts` additively with `imageAspectRatio` on `rich_card` and `carouselCard`, as a positive finite string matching `^\\d+(?:\\.\\d+)?\\s*[/x:]\\s*\\d+(?:\\.\\d+)?$`; reject zero/negative/invalid values at schema validation. Existing `mediaHeight` remains the message-level authoring fallback. Rich-card/carousel fields are `title`, `description`/`subtitle`, `image`, `actions`, and the existing message timing fields. Existing `typing` pseudo-messages and `typingMs`/`showTyping` continue to drive the simulator; delivery/read states are preview/session presentation state, not authored provider messages.

Add `src/live/rcsCompliance.ts` (or equivalent helper extracted from preflight) with `LiveRcsIssue { code, severity: 'error'|'warning', nodeId, messageIndex?, path?, message }`. `preflightLiveRcsFlow(flow, options)` remains the single live compiler and returns `{ success, errors, warnings, nodes, payload, revision }`; `success` means no blocking errors. It consumes a structurally and authored-channel-valid `FlowDefinition`, but defensively returns issues rather than throwing. `validateFlowWithChannelCompliance` remains unchanged in role: `validateFlow` -> `validateChannelCompliance` -> load rejection. Mapping is explicit: structural errors remain `FlowValidationResult.errors`; existing channel-normalizer errors remain blocking load errors; the live preflight rechecks interpolated length/URL/provider mapping and converts equivalent failures to blocking `LiveRcsIssue` with stable codes (`UNSUPPORTED_MESSAGE`, `INVALID_MEDIA_URL`, `INVALID_MEDIA_FORMAT`, `SUGGESTION_LIMIT`, `CARD_LIMIT`, `MISSING_ATTACHMENT`, `INVALID_ACTION`, `TEXT_LIMIT`). Live-only warnings (for example missing image dimensions using a fallback ratio) never alter editor-load behavior. Add compatibility tests proving both entry points reject the same existing hard violations and that preflight adds only live/interpolation findings.

Define exported schemas/types in `src/live/rcsPayload.ts`: `RcsPayload = { version: 'rcs-preview.v1', flowId: string, nodes: Array<{ nodeId: string, content: Array<RcsPayloadContent> }> }`, where content maps the existing compiled plan: `{type:'text', text, suggestions?}`, `{type:'media', mediaType:'image'|'video'|'file', url, ...}`, `{type:'rich_card', title, description?, imageUrl?, actions?}`, and `{type:'carousel', cards:[{id,title,description?,imageUrl?,actions?}], mediaHeight?}`. Actions/replies use the existing stable IDs, labels, and reply routing metadata. `buildRcsPayload` returns `{ payload: RcsPayload, metadata: { revision: string, imageAspectRatioByPath: Record<string,string>, generatedAt?: never } }`; serialization uses `JSON.stringify(payload, null, 2)`, stable node/message order, and omits undefined fields. Aspect ratio is preview metadata only, not a provider transport field. Tests assert an exact deterministic JSON fixture for text, card, carousel, and suggestions.

Aspect-ratio precedence is: valid per-card `imageAspectRatio`; otherwise message `mediaHeight` mapping (`short=2.5/1`, `medium=1.82/1`, `tall=1.5/1`); otherwise orientation (`horizontal=1.82/1`, `vertical=1/1` for rich cards only); otherwise `1.82/1`. Invalid explicit ratios are blocking for that message/card and that image is omitted from payload; other nodes/cards still compile so the UI can identify the exact path. Missing dimensions are non-blocking and use the fallback. Update `src/messages/RichCard.tsx`, `src/messages/Carousel.tsx`, `ImageWithFallback` usage, and shared CSS to apply `aspect-ratio`, `object-fit: cover`, safe fallback dimensions, `overflow-wrap:anywhere`, and no horizontal overflow.

The optional JSON panel is a new `src/components/controls/RcsPayloadPanel.tsx`, adjacent to the visual preview in the existing inspector/demo layout, hidden by default. It has a button with `aria-expanded`/`aria-controls`; valid payloads show formatted JSON and revision, while blocking issues show “Payload unavailable” plus linked issue messages. Compliance findings render in `RcsCompliancePanel.tsx` with `role="status"` for warnings and `role="alert"` for blocking errors.

## Live demo state, persistence, and timing

Refactor `src/components/controls/LiveRcsControls.tsx` around explicit states `idle | loading | ready | error | active`; loading disables start/stop/reset and displays a status text; errors use safe server/client messages and retry. Add Reset demo, which cancels polling, clears credentials/session/projection, clears token/error, restores the initial scenario and phone input, and calls the existing store `restart`. The indicator reads “Demo mode — simulated interaction” for fake mode and “Live mode — sends to the configured RCS test user” for Vonage; it never claims delivery guarantees. Replace the current fallback-number wording with: “Enter any 7–15 digit testing-user number. Leave blank to use the server-configured fallback.” Do a repository copy audit for fixed-number text and remove only stale fixed-number instructions.

Add `src/store/liveDemoPersistence.ts` and a versioned `bmfs.liveDemo.v1` record `{ sourceHash, scenarioId, activeCustomScenarioId?, destinationPhone, phonePlatform? }`. Hash is SHA-256 of UTF-8 `flowSource` using `crypto.subtle` in browser code; because initialization is async, store the hash as a deterministic FNV-1a fallback only if Web Crypto is unavailable, with an algorithm prefix (`sha256:`/`fnv1a:`). Built-ins map by parsed `metadata.id`; custom flows map by `activeCustomScenarioId`, with metadata ID only as a secondary label. Write on `loadFlow`/scenario load, custom scenario activation, destination-phone change (debounced or immediate), and phone-platform change through existing store setters. Extend `persistScenario` without changing shared-link locking.

Initialization order is: shared-link branch (read only, never live-demo restore), preferences, last scenario parse/validation/load, then live-demo record lookup; restore scenario only when hash equals current `flowSource` hash and the stored ID matches the active custom ID or parsed metadata ID. On mismatch, keep the loaded valid flow and default phone; malformed storage is ignored. Reset removes/overwrites this record with the loaded initial scenario and empty phone. Add tests for built-in, custom, source-changed, malformed, shared-link, fresh-session, and arbitrary phone values.

Use `src/live/liveClock.ts` (small injectable `Scheduler` interface: `setTimeout`, `clearTimeout`, `now`) in the simulator/live preview rather than naked timers. Default fake timing is typing at message `typingMs` (or global `typingDurationMs`, capped to 10 seconds), then `submitted` immediately, `delivered` at +500 ms, `read` at +1000 ms; `fastMode` collapses to one scheduler turn. Reset/stop/navigation cleanup cancels all handles. A newer run token wins; terminal `failed|stopped|completed` cannot be overwritten by stale callbacks. Fake-timer tests cover typing cancellation and every status transition. This state is visual/simulated; Vonage status remains authoritative when configured.

Update `src/components/controls/LiveRcsControls.tsx`, `src/live/liveSessionProjection.ts`, and `server/liveDemo.js` only as needed to expose typed delivery/read/typing timeline fields. Add labeled, always reachable phone controls in `PhoneScreen`/its owning layout (inspect existing owner before edit): at small widths place controls in a wrapping toolbar below/above the phone, not absolute-only overlays; retain current presenter/shared-link boundaries.

## Server contract

Normalize all live API errors in `server/app.js` through one allowlist and `{ error: { code, message }, id?, liveSnapshot? }`: `UNAUTHORIZED` 401 “Unauthorized.” (re-authenticate); `LIVE_NOT_CONFIGURED` 503 “Live RCS is not configured.” (configure server); `INVALID_RECIPIENT` 422 “Enter a valid testing-user phone number.” (edit input); `INVALID_FLOW` 422 “The live RCS flow is invalid or not allowlisted.” (fix/load RCS scenario); `LIVE_CONFLICT` 409 “A live RCS session is already active.” (stop/reset it); `SESSION_NOT_FOUND` 404 “Live session not found.” (reset); `DELIVERY_FAILED` 502 “Live message delivery failed.” (retry/reset); `LIVE_UNAVAILABLE` 503 “Live RCS is temporarily unavailable.” (retry). Unknown exceptions map to `LIVE_UNAVAILABLE` and log only server diagnostics. Apply this to create/list/logs/get/stop/restart and the missing-session GET (currently raw string), and preserve recovery `id/liveSnapshot` on create/restart delivery failure. Client `api()` parses only this envelope, maps unknown codes to the generic safe message, and uses an embedded snapshot as recoverable active state.

## Selectors and accessibility

Make `src/components/controls/BrandIcon.tsx` export a reusable `BrandIcon({brand, decorative?, label?})`; use official-looking local SVG paths for all four brands, with `aria-hidden` when decorative and an accessible label otherwise. Update `ChannelSelector.tsx` and `PhonePlatformSelector.tsx` to use option metadata (`label`, description, brand colors, contrast-safe text), `aria-describedby`, and roving tab index: selected radio `tabIndex=0`, others `-1`; Arrow keys move and focus, Home/End jump, Space/Enter select. Compare mode leaves the group in the DOM with `aria-disabled=true`, `tabIndex=-1` on radios, and focus on the compare toggle; Escape or toggling Compare returns focus to the selected radio. No `pointer-events-none`-only disabling.

Use full-surface brand colors but a concrete contrast matrix: RCS `#1A73E8`/white (7.0:1), WhatsApp `#128C7E`/white (4.6:1), iPhone `#111827`/white (17.7:1), Android `#137A46`/white (5.5:1); hover darkens at least 10%, checked adds a 2px outline/checkmark and unselected uses a neutral border plus “Not selected” semantics, disabled uses `#64748B`/white (4.7:1). Focus is a 3px `#F8FAFC` outer ring plus dark offset. Add `@media (forced-colors: active)` with `ButtonText`, `ButtonFace`, `Highlight`, and outline/checkmark state so meaning survives neutral fallback. Add a small description/tooltip (`title` plus visible responsive detail) for each option. Add CSS `@media (prefers-reduced-motion: reduce)` to disable carousel smooth scrolling, typing bounce, and nonessential transitions.

## Review findings addressed

1. Compliance boundary: retained editor validation and made live preflight a downstream, mapped compiler with compatibility tests.
2. RcsPayload: defined exact exported shape, serialization and fixture expectations.
3. Server errors: defined exhaustive endpoint-wide allowlist, statuses, messages, recovery, and missing-session handling.
4. Persistence: defined hash algorithm, IDs, writes, initialization order, mismatch and share-link behavior.
5. Authoring surface: existing YAML/JSON Scenario Editor/imported flows, with explicit end-to-end test.
6. Aspect ratio: defined precedence, exact ratios, fallback, and per-card blocking scope.
7. Timing: injected scheduler, exact timings, cancellation, terminal precedence, and fake timers.
8. Compare keyboard behavior: defined focus, tab order, key actions, and exit path.
9. Contrast/fallback: supplied color matrix, ratios, forced-colors CSS, and state indicators.
10. Stale copy: supplied replacement wording and required copy audit.
