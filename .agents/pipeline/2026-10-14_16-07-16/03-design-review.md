# Design Review

## Findings

1. **HIGH — The live preflight/payload contract is internally inconsistent and not implementable as specified.** In “State, validation, and payload model,” `preflightLiveRcsFlow` is said to return `{ success, errors, warnings, nodes, payload, revision }`, while the proposed `rcsPayload.ts` separately builds a payload and the existing `src/live/rcsPreflight.ts` currently returns only `{ success, errors, nodes }`, with `LiveRcsIssue` having no severity/code/path. The design also says payload generation corresponds to the “current valid configuration,” but does not define whether warnings make `success` true, whether `payload` is present when there are per-card errors, or how `revision` is calculated. **Fix:** define one exact TypeScript result, e.g. `{ success: boolean; errors: LiveRcsIssue[]; warnings: LiveRcsIssue[]; nodes: LiveRcsNodePlan[]; payload: RcsPayload | null; revision: string }`, state that `success === errors.length === 0`, and specify that any error yields `payload: null` (or explicitly define partial payload semantics). Define deterministic revision input and `path` values and update all consumers/tests to that contract.

2. **HIGH — Delivery/read/typing requirements are not connected to the existing projection schema or UI.** The design proposes “typed delivery/read/typing timeline fields” and exact simulated timing, but `src/live/liveSessionProjection.ts` currently accepts snapshot statuses only as `starting | awaiting_reply | completed | error | stopped`, has no delivery/read/typing event schema, and maps timeline items only to renderable messages. `LiveRcsControls.tsx` only displays the session status/activity and has no message-status presentation. The design does not specify the event shape, state precedence, rendering component, or how Vonage provider statuses map to these states. **Fix:** define a versioned timeline/status union (including `typing`, `submitted`, `delivered`, `read`, `failed`), specify server fake-session emission and Vonage mapping, and name the preview component/fields that render each state; define fallback behavior for unknown provider statuses and stale snapshots.

3. **HIGH — Persistence design does not specify a valid source of `flowSource` or preserve the existing shared-link storage guarantee.** The design requires a SHA-256 hash of `flowSource`, writes on several store setters, and says “extend `persistScenario`,” but the existing `src/store/persistence.ts` `StoredScenario` contains only source/format/variables/brand, while `src/store/simulatorStore.ts` has a separate shared-link lock that must never read or write local storage. The proposed initialization order (“preferences, last scenario parse/validation/load, then live-demo record lookup”) can restore a live record in a shared-link or invalid-load path unless the lock/branch is explicitly enforced. It also does not define behavior when `crypto.subtle` is unavailable during async initialization or when a setter runs before the hash is ready. **Fix:** specify exact changes to `StoredScenario`/`persistScenario`, a `loadLiveDemoPersistence` guard `if (sharedLinkMode) return null`, and an initialization state machine that never restores or writes in shared-link mode; define canonical source bytes, hash readiness, and queued/debounced writes. Add tests asserting localStorage is unchanged for every shared-link path and that a valid loaded flow is never overwritten by a stale record.

4. **HIGH — Rich-card aspect-ratio support is incomplete for the required authoring and rendering path.** The design adds `imageAspectRatio` to `rich_card` and `carouselCard`, but the existing schema has `mediaHeight` on `rich_card` and on `carousel` (not on each carousel card), and `src/messages/RichCard.tsx` currently uses fixed height classes rather than an aspect ratio. The proposed precedence mentions `message.mediaHeight` for a carousel card but does not define where that value comes from or how an explicit per-card ratio reaches `NormalizedMessage`; it also says invalid ratios are blocking “for that message/card” while the existing editor validator rejects an invalid whole flow. **Fix:** define the exact schema fields and normalized/rendered types for both message kinds, specify the carousel-level versus card-level precedence, and state whether invalid ratios are editor-blocking or live-only issues. Include fixtures proving YAML → validated flow → normalized preview → payload preserves the intended ratio.

5. **HIGH — Error handling and recoverability are not aligned with the current client/server contract.** The design requires an endpoint-wide allowlist with `INVALID_RECIPIENT`, `INVALID_FLOW`, and `LIVE_UNAVAILABLE`, but current `server/app.js` maps messages to `LIVE_INVALID_REQUEST` and `LiveRcsControls.tsx` parses either a string or `{message}` error. The design says `api()` “parses only this envelope” and uses recoverable snapshots, but does not define behavior for malformed/non-JSON responses, authentication failures, diagnostics failures, polling 404/session expiry, or reset failure. It also says loading disables reset, while reset is the required recovery path and must cancel/clear state. **Fix:** specify the exact `api()` error type and fallback for every non-envelope response, endpoint-to-code mapping for diagnostics and all CRUD operations, and the state transition table for retry/reset/stop, including whether Reset remains enabled while loading and how a failed reset is surfaced without losing the last valid snapshot.

6. **MEDIUM — The selector requirements are under-specified relative to the existing two independent radiogroups and comparison mode.** `ChannelSelector.tsx` and `PhonePlatformSelector.tsx` already use radio roles, but channel currently disables the entire group with `pointer-events-none` in compare mode and has no keyboard roving behavior, descriptions, explicit unselected semantics, or focus restoration. The design specifies roving behavior for channel/platform but only gives a compare-mode rule for “the group,” without stating whether compare mode applies to the phone platform group, how Arrow keys wrap, or how a selected option is announced when focus moves without selection. **Fix:** define separate keyboard/state tables for each group (including wrap/no-wrap, RTL behavior, Space/Enter, and Escape), explicitly state compare-mode behavior for both groups, and require `aria-describedby` IDs plus visible “Selected/Not selected” text or an equivalent non-color indicator. Add acceptance tests for tab order and focus restoration.

7. **MEDIUM — “Official logos” are not satisfied by the design’s “official-looking local SVG paths.”** The requirement asks for official logos and accessible reusable components, but the design only says “official-looking local SVG paths.” The existing `BrandIcon` uses lucide speech icons for RCS/WhatsApp and has no `decorative`/`label` API, so “official-looking” leaves both asset provenance and semantic treatment unresolved. **Fix:** name the approved local assets/paths and their license/provenance, define `BrandIcon({ brand, decorative?, label? })` behavior for decorative versus meaningful use, and add tests ensuring accessible branding names without duplicated announcements.

8. **MEDIUM — Responsive/zoom acceptance is not translated into concrete layout constraints or verification.** The design requests small-width wrapping for phone controls and reduced motion, but does not identify the actual owner/layout that places the controls, nor specify how the adjacent payload and compliance panels reflow at 200% zoom. Existing `PhoneScreen.tsx` contains only the channel renderer and no preview-control toolbar, so the design’s “inspect existing owner before edit” is an implementation instruction rather than a design contract. **Fix:** identify the owning layout and define breakpoints/reflow rules (including payload stacking, carousel controls, focus visibility, and overflow behavior) for mobile/tablet/desktop and 200% zoom; list the exact manual checks and expected outcomes when no browser automation exists.

9. **MEDIUM — Scope and compatibility boundaries conflict around channel validation.** The design says `validateFlowWithChannelCompliance` remains unchanged in role and that existing hard violations are rejected identically, but it also adds new `imageAspectRatio` validation and says live preflight rechecks equivalent failures. Existing `validateChannelCompliance` runs the actual WhatsApp and RCS normalizers at scenario load, while the design’s live-only warnings and partial per-card compilation could produce a preview that load validation never understands. **Fix:** provide a compatibility matrix for structural schema errors, channel-normalizer errors, live-only warnings, and payload errors, with the exact gate that owns each issue. Explicitly state whether new rich-card/carousel fields are accepted by both channel normalizers or ignored/rejected for WhatsApp without changing existing supported flows.

10. **NIT — The stale-copy replacement is not precise enough for arbitrary input formatting.** The proposed wording says “7–15 digit testing-user number,” while the current server accepts an optional `+` and removes spaces/hyphens before validating. **Fix:** document the accepted input grammar in the UI copy and validation (`+` plus 7–15 digits, with allowed separators if retained), and add a client-side actionable validation message before the request.

## Verified Assumptions

- `src/schema/messages.ts` currently supports rich cards, carousels, suggestions, typing pseudo-messages, and `typingMs`/`showTyping`, but does not currently define `imageAspectRatio`.
- `src/live/rcsPreflight.ts` currently emits only blocking-looking `errors`, supports only reply/open_url live actions, and returns no payload, warnings, or revision.
- `src/live/liveSessionProjection.ts` currently validates a limited live snapshot/status model and does not model delivery/read/typing timeline states.
- `src/components/controls/LiveRcsControls.tsx` already has a basic loading spinner for start/stop and polling, but has no Reset demo action, persistent demo-mode indicator, or navigation persistence for destination phone.
- `src/components/controls/ChannelSelector.tsx` and `PhonePlatformSelector.tsx` use `role="radiogroup"`/`role="radio"`, but do not implement roving tab index or compare-mode focus behavior; channel compare mode uses `pointer-events-none`.
- `src/components/controls/BrandIcon.tsx` currently exposes only `{ brand }`, marks all icons decorative, and uses lucide icons for RCS and WhatsApp.
- `src/messages/RichCard.tsx` uses fixed media-height classes, while `src/messages/Carousel.tsx` already applies ratios for carousel-level `mediaHeight` and uses smooth scrolling.
- The server currently validates arbitrary recipients to 7–15 normalized digits and supports a configured fallback, but its current error mapping uses `LIVE_INVALID_REQUEST` rather than the design’s proposed exhaustive code set.
- Shared-link mode in `src/store/simulatorStore.ts` locks persistence writes and intentionally skips visitor preferences/scenario restoration; any new persistence path must preserve that invariant.

## Unverified/Wrong Assumptions

- The design’s assertion that extending `preflightLiveRcsFlow` can cleanly provide warnings, payload, revision, and partial per-card compilation is not verified; the current function and its consumers have no such contract.
- The design’s claim that typed delivery/read fields can be exposed with only the listed live projection/server changes is incomplete; the current snapshot schema and preview UI require an explicit event and rendering design.
- The design does not establish that `flowSource` hashing via `crypto.subtle` is available at every store write point or that the proposed FNV-1a fallback remains stable across runtimes.
- “Official-looking local SVG paths” is not equivalent to verified official logo assets or an identified usage license.
- The design does not verify that the proposed aspect-ratio fields can flow through the current normalization and preview types without altering WhatsApp compatibility behavior.
