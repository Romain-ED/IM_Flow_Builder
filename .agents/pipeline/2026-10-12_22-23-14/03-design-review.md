# Design Review: Live-demo phone state mirror

## Findings

1. **HIGH — The presenter DTO is not implementable as written because `LiveRenderableMessage` is never defined.** The “Server contract and data ownership” section names a closed union (`text`, `image`, `video`, `document`, `rich_card`, `carousel`, `suggested_replies`, and `suggested_actions`) but does not define the fields, nullability, `sender` placement, card/action shape, or how a user item differs from a business item. The existing renderer consumes `RenderableMessage` from `src/schema/messages.ts`, where document uses `filename`/`fileType`, rich cards use `image`, and carousel cards use `image`/`subtitle`/`price`/`badges`; the current server transport objects instead use `file`, `card`, and `imageUrl`. “Maps server `document` to renderer's `document`” is not a sufficient contract. **Concrete fix:** add an exact discriminated TypeScript/JSON schema (preferably shared or duplicated with parity tests), for example `{ type: 'text', sender: 'user'|'business', text: string }`, `{ type: 'document', sender, url?: string, filename: string, title?: string, description?: string, fileType?: string }`, and explicit card/carousel/action fields. Include representative JSON fixtures for every supported variant and state whether unsupported fields are stripped or rejected.

2. **HIGH — The authoritative server validation/compiler has no defined implementation boundary.** The design says the server performs Live RCS compilation/validation and that the client `rcsPreflight` reports the same errors, but `src/live/rcsPreflight.ts` is TypeScript client code and cannot be imported by the Node server as specified. No new server compiler module, function signature, input/output contract, or parity strategy appears in “Files to modify or add”; the current `LiveDemoService.createSession` only performs shallow flow checks and `collectContent` can throw during sending. **Concrete fix:** define and add a server-side `compileLiveRcsFlow(flow, { publicBaseUrl })` (for example in `server/liveRcsCompiler.js`) returning `{ success, errors, nodes }`, call it before creating/persisting a session, and add shared fixture tests proving server and client reject/accept the same cases. If the implementation intentionally duplicates the compiler, state which limits and URL rules must remain identical.

3. **HIGH — API compatibility and response migration are underspecified and conflict with current consumers.** The design says all session/list/restart/stop results replace `sessionView()` with the new snapshot, while claiming existing consumers remain compatible because `id` and `status` stay top-level. Current `LiveRcsControls.tsx` reads `events`, and `LiveDiagnosticsPage.tsx` reads `session.events` and `session.outbound`; those consumers cannot continue working from only `id`/`status`. The design also changes errors from the current string envelope (`{ error: string }`) to `{ error: { code, message } }` without defining whether every endpoint is migrated atomically or whether a versioned endpoint/envelope is introduced. **Concrete fix:** specify the exact response for each endpoint, including list summaries, `GET /sessions/:id`, restart, stop, logs, and failed create/restart. Choose one migration: either update every listed client consumer in the same change and formally make the new DTO the v1 contract, or retain a documented legacy response and add a separate `snapshot`/versioned endpoint. Add contract tests that assert both the new shape and the intended legacy behavior.

4. **HIGH — Timeline persistence and concurrency rules are missing.** The design requires stable IDs, persisted ordinals, bounded history, coherent restart, and saving after every externally visible mutation, but it does not define the persisted session schema/migration from the current store. `normalizeStore` currently returns old sessions unchanged, and existing sessions have no timeline or ordinal counter. It also does not define serialization for concurrent inbound/status/restart operations; two requests can otherwise append with ambiguous order or operate on a session after restart. Persisting after a provider send still leaves a crash window in which a provider message is sent but its timeline item is not saved. **Concrete fix:** define `session.schemaVersion`, `timeline`, `nextTimelineOrdinal`, and a `normalizePersistedSession` migration policy (old sessions must be safely migrated or excluded from presenter endpoints). Serialize mutations per session, allocate the ID/ordinal before the send, specify the commit/recovery behavior for a send/save crash, and make the sort/deduplication rule explicit. Add tests for restart plus repeated and overlapping inbound/status requests.

5. **HIGH — The proposed `open_url` action cannot be mapped to the existing client model while omitting its URL.** The design says the URL must not be returned and that the action is mapped to a disabled client action, but `Action` in `src/schema/messages.ts` requires `{ type: 'open_url', label: string, url: string }`. `ActionButton` accepts that `Action` union. Constructing `{ type: 'open_url', label }` is a TypeScript error; casting it would leave an invalid object and makes accidental URL use possible. **Concrete fix:** introduce a separate `LiveDisplayAction`/`LiveDisplayChoice` render type whose `kind` is `open_url` and has only a label, or add an explicit `readOnly` action prop/type to the renderer. Make the mapping exhaustive for reply versus display-only actions and test that no URL or routing fields occur in the serialized snapshot.

6. **HIGH — The read-only rendering design does not specify a complete path that prevents all local side effects.** The current `ConversationView` computes attachments from `history`, creates trailing action callbacks, renders `ChoiceChips` with store handlers, and `MessageRenderer` derives interactivity from the local store's `currentNodeId`. `VideoMessage` and `DocumentMessage` directly call `showToast` even though they have no `interactive` prop; other current renderers call `handleAction`, `simulateCardAction`, `openListSheet`, `handleOtpSubmit`, or download/open-preview handlers. The design says to “thread” `readOnly` and suppress overlays, but does not define the `MessageRenderer`/`ConversationView` signatures or how trailing callbacks and store lookups are disabled for a live timeline. **Concrete fix:** define `MessageRenderer({ message, channel, readOnly, trailingActions? })` and make the live `ConversationView` branch pass `readOnly: true`, never build local trailing/pending callbacks, and use only the projected entries. Every callback-bearing renderer must receive the flag and render a non-button/passive view; component tests must click every live content/action path and assert no store mutation, toast, modal, download, or local transition.

7. **HIGH — Behavior when live mode is active before a valid projection exists is unspecified and can violate the isolation requirement.** The design says `liveSessionActive && liveProjection` selects the server timeline, but gives no branch for `liveSessionActive && !liveProjection`. The existing phone renders `history`, so a naïve conditional leaves stale local conversation visible during startup, invalid-snapshot rejection, or a first-fetch failure. That contradicts the requirement that server data is the source while live mode is active and that local history is isolated. **Concrete fix:** define the selection as “if live mode is active, always render the live branch; use `liveProjection?.timeline ?? []` and an explicit unavailable/loading indicator, never local `history`.” Preserve the last valid projection on fetch/projection errors, and define what is shown when there has never been a valid snapshot. Add a test for start-before-first-fetch and fully invalid snapshots.

8. **HIGH — The inbound recognition and timeline-ordering contract is not precise enough to guarantee the required user-before-business sequence.** The design refers to recognized replies/text and says an inbound item is appended “before or alongside” resulting business messages, but does not define the accepted payload locations, required event-id behavior, duplicate semantics, text trimming/display text, the node ID attached to a user item, or the behavior when an input/choice has no `next`. The current source searches several postback locations, accepts `payload.text` or `payload.message.text`, records duplicates by `message_uuid`, and permits optional `next` in the authored schema. The phrase “before or alongside” permits different valid ordering across polling responses. **Concrete fix:** specify a normalization result such as `{ recognized: boolean, eventId: string, sender: 'user', nodeId: currentNodeId, message: ... }`, require and persist the deduplication key, define exact extraction precedence and sanitization, append the user item with an ordinal before routing, and append resulting outbound items afterward. Explicitly choose and test no-target semantics (reject at validation, or recognize and remain on the current node); do not rely on an implementation convention.

9. **MEDIUM — Provider-status normalization is incomplete.** `LiveSnapshot.provider.latestStatus` is a closed enum, but the design never states how arbitrary provider values in `payload.status`/`message_status` are mapped, whether status transitions are monotonic, what timestamp is used, or what happens for an unknown status. The current `handleStatus` stores any provider string directly in `outbound.status`, so simply exposing it would violate the closed DTO. **Concrete fix:** define an allowlist/mapping table (including casing and Vonage-specific values), map unknown values to a documented `updated` state or ignore them with a safe diagnostic, set `provider.updatedAt` from the callback receipt time, and test repeated/out-of-order/unknown callbacks. Provider status must never enter `timeline` or mutate the latest inbound/outbound activity fields.

10. **MEDIUM — Secret and URL redaction is not executable enough for the stated least-exposure requirement.** The design describes key-name and credential-pattern masking, but does not define a complete recursive redaction policy for every nested renderable field and activity preview, nor a policy for media URLs. Existing `resolveMediaUrl` can return authored URLs unchanged, and URLs may contain credentials or signed query parameters; the provider error path currently includes bounded provider detail in an `Error.message`, which is then recorded by `app.js` diagnostics. “Bounded” is not equivalent to safe. **Concrete fix:** define one recursive `sanitizePresenterValue` used for variables, interpolated text, previews, diagnostics, and every nested message/action field. Reject or strip URL userinfo and query parameters containing credential/signature keys (or explicitly allow only an approved public URL form), and replace provider errors with fixed safe codes before recording or returning them. Add serialized-output tests that search presenter, diagnostics, error, and media URL JSON for fixture secrets, tokens, private values, provider IDs, webhook IDs, and raw payload fragments.

11. **MEDIUM — The public-variable extension has no compatibility/defaulting rule.** The design adds `metadata.livePublicVariables`, but the actual `FlowMetadata` schema has no such field and the current flow editor/persistence format has no authoring or migration behavior for it. It also states limits for keys/values without saying whether these are enforced when a flow is parsed, when a session is created, or only during projection. Existing flows must not accidentally publish all variables or fail merely because the field is absent. **Concrete fix:** add an optional schema field with an explicit default of `[]`; define how it is preserved through YAML/JSON import/export and custom-scenario save; enforce key/value limits and sensitive-name denial at server session validation; and specify that absent/invalid metadata publishes no variables rather than falling back to the internal map.

## Verified Assumptions

- `server/app.js` already exposes authenticated live session create/list/get/restart/stop routes, and `LiveRcsControls.tsx` already polls `GET /api/live/sessions/:id` immediately and every 2,500 ms while active.
- `server/liveDemo.js` owns live flow execution, provider sends, inbound handling, status handling, and file-backed session persistence; `FakeRcsGateway` provides a test seam.
- The current phone renderer has established normalized messages in `src/engine/types.ts` and supports text, image, video, document, rich-card, carousel, suggested-reply, and suggested-action message components, among other simulator-only types.
- The current local simulator state is not isolated from live state yet: `SimulatorState` has `history`, local variables/node state, and only `liveSessionActive`, `liveSessionId`, and `liveOperatorToken`; there is no `liveProjection` or live sync status.
- The existing phone composer already prevents local text submission while `liveSessionActive` is true and offers a restart control, but the restart store action currently only displays a toast and does not install the returned server snapshot.
- `src/schema/messages.ts` permits optional `next` on authored choices, reply actions, and input messages. The design's choice to reject no-target live interactions is a new compatibility rule, not an existing invariant.
- `src/schema/flow.ts` currently has no `metadata.livePublicVariables` field.

## Unverified/Wrong Assumptions

- The assumption that `sessionView()` is already safe is wrong. It removes `flow`, `correlation`, `processedInbound`, and `publicBaseUrl`, but currently leaves `variables`, `outbound` (including provider message IDs and transport content), and `events` in session responses.
- The assumption that diagnostics are already a separate safe surface is wrong for the current implementation. `diagnosticsLog()` returns `sessionView(session)` and the unfiltered `diagnosticEvents`; `app.js` also records error messages and inbound summaries. The existing diagnostics page explicitly displays/copies `events`, `outbound`, and arbitrary diagnostic records.
- The assumption that route errors already use stable typed envelopes is wrong. `app.js:apiError` classifies errors by message substring and returns `{ error: string }`; unauthorized and not-found branches also return string errors. Typed errors and deterministic `{ error: { code, message } }` are design work, not existing behavior.
- The assumption that current server validation is authoritative and equivalent to client preflight is wrong. The server currently checks only a few flow properties before `collectContent`; the client compiler is a separate TypeScript module, and no server-side compiler contract exists.
- The assumption that current renderers are passive when `interactive` is false is wrong for all required live paths. `VideoMessage` and `DocumentMessage` always expose click handlers that call `showToast`, and several other message renderers directly access simulator handlers or overlays. A read-only implementation must make this behavior explicit rather than relying on existing `interactive` props.
- The assumption that existing persistence can transparently provide the new timeline is unverified/wrong: the current store normalizer only checks for `sessions` and performs no session-shape migration, timeline initialization, or stable-ordinal recovery.
