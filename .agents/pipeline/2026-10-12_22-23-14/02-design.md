# Technical Design: Live-demo phone state mirror

The feature will add a server-authoritative semantic conversation projection for an active Live RCS session. The server will persist a bounded, normalized timeline of business messages and recognized user replies, expose it through an allowlisted versioned snapshot, and keep provider/routing diagnostics separate. The client will validate that snapshot at a projection boundary, store it in a dedicated Zustand branch, and render it read-only in the existing phone while live mode is active. Normal simulator history and interaction state will remain untouched; this represents the known flow conversation and node position, not the native handset viewport.

## Technology and repository fit

The stack is the existing Node.js ES-module HTTP server, plain JavaScript service layer, React 19/TypeScript, Zod, Zustand, Vitest, Vite, and Tailwind utility classes. No dependency, socket, or second polling mechanism is needed. The existing authenticated `/api/live/sessions/:id` endpoint and `LiveRcsControls` 2,500 ms interval remain the transport and cadence. `server/liveDemo.js` owns flow execution and persistence; `server/app.js` owns authentication, HTTP envelopes, and webhook routing; `src/live/rcsPreflight.ts` remains the client-facing Live RCS compiler; `src/live/liveSessionProjection.ts` becomes the client validation/mapping boundary.

## Server contract and data ownership

`server/liveDemo.js` will replace public uses of the current broad `sessionView()` with an explicit `presenterSnapshot(session)` DTO. The existing session object may continue to contain `flow`, internal variables, correlation entries, processed inbound IDs, provider IDs, transport content, and the public base URL in memory/file storage, but none of those fields will be serialized by presenter endpoints. All presenter session, list, restart, stop, and inbound/status results use this shape:

```ts
interface LiveSnapshot {
  schemaVersion: 1
  id: string
  status: 'starting' | 'awaiting_reply' | 'completed' | 'error' | 'stopped'
  currentNodeId: string | null
  pendingInput: { nodeId: string; inputType: 'text' | 'email' | 'phone' | 'numeric' | 'date' } | null
  variables: Record<string, string | number | boolean | null>
  timeline: LiveTimelineItem[]
  timelineTruncated: boolean
  activity: {
    latestInbound: LiveActivity | null
    latestOutbound: LiveActivity | null
    latestProvider: LiveActivity | null
  }
  provider: { latestStatus: 'submitted' | 'delivered' | 'read' | 'rejected' | 'undeliverable' | 'failed' | 'updated' | null; updatedAt: string | null }
  updatedAt: string
}

interface LiveTimelineItem {
  id: string                 // generated once and persisted with the item
  ordinal: number            // persisted tie-breaker for equal timestamps
  at: string                 // ISO timestamp
  nodeId: string | null
  sender: 'business' | 'user'
  message: LiveRenderableMessage
}

interface LiveActivity {
  at: string
  nodeId: string | null
  preview: string             // sanitized, at most 240 Unicode scalar values
  kind: 'inbound' | 'outbound' | 'provider'
}
```

`LiveRenderableMessage` is a closed JSON union containing only the client-supported RCS projection: `text`, `image`, `video`, `document`, `rich_card`, `carousel`, `suggested_replies`, and `suggested_actions`. Every variant carries only display data and `sender`; media URLs, filenames, titles, descriptions, card metadata, and action/reply labels are bounded. Reply/action targets (`next`, `set`, correlation IDs, and routing payloads) are intentionally absent. An `open_url` action is represented as a display-only action kind/label and is mapped to a disabled client action; its URL is not returned. The transport-only server forms (`file`, `card`, and action objects with routing fields) are converted to this DTO before persistence. User replies are `text` messages whose text is the recognized authored label; recognized free text is a `text` message containing the sanitized received text. Unrecognized inbound activity does not enter `timeline`.

The timeline is appended only after a provider send succeeds, or immediately when the server recognizes an inbound reply/text before routing the next node. IDs and ordinals are persisted, so unchanged polling is byte-stable for timeline identity and ordering. The server bounds the timeline to 500 items, removes the oldest items if necessary, and sets `timelineTruncated: true`; it never fabricates typing, delay, input, or provider messages. Pending input is represented only by `pendingInput`, including its node and input type; the input variable name is not public. Provider delivery updates change `provider` and `activity.latestProvider`, never `timeline`.

`variables` is an explicit presenter-safe subset, not the internal variable map. Add optional `metadata.livePublicVariables: string[]` to `src/schema/flow.ts`. Keys are at most 64 Unicode scalar values, values at most 256, and only keys in this allowlist are exposed. Keys containing sensitive terms (`password`, `secret`, `token`, `key`, `credential`, `auth`, `otp`, `pin`, `verification`, or `code`) are never publishable even when listed; values matching credential/JWT/bearer/private-key patterns are masked. Unknown/private interpolation in safe timeline content is replaced with `[hidden]`, while the actual provider transport can still use the internal value. User text is compared against private variable values and the same credential patterns before publication; matches are replaced with `[redacted]`. This is enforced in the server normalizer before both timeline and activity construction, so a neutral key such as `verificationCode` cannot leak through either `variables` or interpolated text. Public labels are capped at 160 scalar values and previews at 240, using `Array.from(value).slice(0, limit)` plus an ellipsis so truncation is Unicode-safe.

The diagnostics endpoint remains available but gets a separate `diagnosticsDto`, rather than returning `sessionView`. Its allowlist is `{ generatedAt, session: { id, status, maskedRecipient, flowId, currentNodeId, createdAt, updatedAt, outboundCount }, diagnostics: [{ id, at, type, nodeId?, status?, recognized?, messageType?, safeCode?, safePreview? }] }`. It omits provider message IDs, transport message bodies, action routing fields, all variable values, correlation/processed inbound IDs, webhook payloads, recipient addresses beyond the existing mask, credentials, and public URLs. `safePreview` is used only for bounded non-secret summaries; inbound text and reply labels use length/type summaries unless already passed through the same redactor. `id` is a generated diagnostic display index, not an internal event or provider identifier. `LiveDiagnosticsPage` will consume this allowlist and remains the troubleshooting surface; it does not receive the presenter timeline's message bodies.

## Server lifecycle and validation

`createSession`, `restartSession`, `handleInbound`, `handleStatus`, `stopSession`, `getSession`, `listSessions`, and `diagnosticsLog` will all return a presenter snapshot or the explicit diagnostics DTO; no caller will serialize the internal session directly. Creation saves the new internal session before entering the start node and saves after each successful provider send. This makes an already-created partial run durable. On any provider failure, it sets status `error`, records only a fixed safe diagnostic code, persists the partial state, and throws a typed delivery error carrying the session ID and the current presenter snapshot.

The successful create response remains HTTP 201 with the snapshot fields at the top level (`id`, `status`, etc.), so existing clients that read `id` and `status` remain compatible. The typed failure response is HTTP 502 with `{ error: { code: 'DELIVERY_FAILED', message: 'Live message delivery failed.' }, id, liveSnapshot }` whenever a session was created. The client can therefore install and poll a failed partial run instead of losing it. Restart resets the current timeline, outbound records, correlations, processed inbound IDs, pending input, provider summary, variables, and status to a new starting run under the same session ID; it saves before sending and follows the same partial-failure contract. A restart never appends old-run messages to the new projection.

Before any send, the server performs authoritative Live RCS compilation/validation; client preflight remains an early user-facing check but is not a trust boundary. It validates a plain flow object, RCS channel, allowlisted flow ID, node IDs/references, bounded message/action counts and strings, public media URL rules, and scalar variables. Every Live RCS reply/choice that can be received (`node.actions`, suggested replies, reply actions on cards/carousels) must have a `next` target; every live input must have a `next` target. This deliberately rejects the existing schema's optional no-target reply as `LIVE_FLOW_INVALID` rather than creating ambiguous recognized/no-transition behavior. `open_url` remains non-routing and is display-only in the mirror. The client `compileAction`/`compileChoices` and input compilation will report the same preflight error, and the server repeats it against untrusted request JSON.

The server owns these invariants: the selected flow is allowlisted; node transitions reference existing nodes; only recognized replies/text create user timeline items; a timeline item is appended once; timeline IDs never change; provider callbacks can update only a matching internal outbound record; private fields never cross an API projection boundary; and session state is persisted after each externally visible mutation. Client code owns only rendering invariants: malformed snapshots cannot reach a renderer, unsupported items are skipped with a safe warning, and live projection writes cannot mutate local simulator state.

## HTTP errors and recoverability

Add typed service errors in `server/liveDemo.js` (or a small server error module if shared by tests): `LiveValidationError` (`422`, `LIVE_FLOW_INVALID`), `LiveNotFoundError` (`404`, `SESSION_NOT_FOUND`), `LiveConfigurationError` (`503`, `LIVE_NOT_CONFIGURED`), `LiveConflictError` (`409`, `LIVE_SESSION_ACTIVE`), and `LiveDeliveryError` (`502`, `DELIVERY_FAILED`, with optional safe snapshot/id). `server/app.js:apiError` maps these types/codes deterministically and always returns `{ error: { code, message } }`; it never uses message substring matching or provider `Error.message`. Malformed JSON/body limits return fixed `400` codes, missing bearer authorization returns `401` with the same stable `{ error: { code: 'UNAUTHORIZED', message: 'Unauthorized.' } }` envelope, and provider detail is logged only as a bounded internal server diagnostic after removing payload content.

Authenticated create/get/list/restart/stop/log operations return the fixed code/message for validation, missing session, configuration, conflict, or delivery failures. A failed create/restart with a persisted session returns the recovery envelope described above; a failure before a session exists returns only `502` and no ID. GET failures retain the last valid client projection and show stale/error state. Webhook signature failures remain `401`; malformed or identity-invalid callbacks use a fixed `WEBHOOK_INVALID`/`422` response; unmatched sessions use `SESSION_NOT_FOUND`/`404`; provider processing failures use the same `DELIVERY_FAILED`/`502` envelope only if a session exists. Webhook diagnostics contain event type, bounded code, and lengths—not the raw webhook, event IDs, postback IDs, or text.

## Client projection boundary

Create `src/live/liveSessionProjection.ts`. It will define the TypeScript DTO types and Zod schemas for the versioned snapshot, enforce maximum array/string/timestamp bounds, and map the closed server union to `NormalizedMessage` from `src/engine/types.ts`. Mapping is pure and has no Zustand or React dependency, making it unit-testable. It sorts by `(at, ordinal)`, de-duplicates by stable `id`, parses ISO dates to renderer timestamps, maps an unknown/null node to the fixed internal `LIVE_UNKNOWN_NODE_ID` sentinel, maps server `document` to the renderer's `document`, `card` to `rich_card`, and `imageUrl` to the renderer's `image`. It maps display-only server actions to client actions with no routing target; these are always passed `interactive: false` in live mode.

A malformed item, invalid timestamp, unsupported message kind, unsupported action variant, or invalid optional field is omitted from the projected timeline and increments a bounded `projectionWarnings` count. The snapshot remains usable; a fully invalid snapshot is rejected and never replaces the last valid state. No projection helper calls `goToNode`, `applyInteractionResult`, `handleAction`, or any local engine function.

Extend `src/store/simulatorStore.ts` with a separate `liveProjection` state and `liveSyncState: 'idle' | 'fresh' | 'stale' | 'error'`, `liveLastSyncedAt`, and `liveSyncError`. `syncLiveSnapshot` validates/maps and atomically replaces only this branch; `markLiveProjectionStale` retains the last valid projection; `clearLiveProjection` clears it. `setLiveSessionActive(false)` clears projection, sync metadata, credentials, and the presenter state; it does not touch `history`, `variables`, `currentNodeId`, `snapshots`, or local events. Starting active mode stops local playback but does not reset local history. `restartLiveSession` installs the successful returned snapshot immediately; it also installs a `liveSnapshot` from a `DELIVERY_FAILED` envelope and reports the error while leaving live mode active.

The controls own the one existing polling effect. After start, it sets credentials, enables live mode, installs the returned snapshot immediately, and runs the same immediate fetch plus 2,500 ms interval. Poll errors call `markLiveProjectionStale` and show the existing error notice without overwriting the last valid timeline. Stop clears the live branch only after the stop request succeeds. The start recovery envelope sets the session ID from `id`, enables live mode, stores the partial/error snapshot, and begins polling. The sidebar no longer maintains a competing authoritative `session`; its summary reads the store projection used by the phone.

Every public store mutation that changes simulator context gets an early live guard before parsing, validation, persistence, or `set`: `loadScenarioSource`, `loadBuiltInScenario`, `loadCustomScenario`, `loadFlow`, custom scenario import/save/delete/duplicate, `setChannel`, `setPhonePlatform`, `setStartNodeOverride`, configured variable and brand setters/resets, and `toggleCompareMode`. Existing guards remain and are added before `pushSnapshot` in `handleChoice`, `handleListRowSelect`, `handleInputSubmit`, `handleFreeText`, and `handleOtpSubmit`. Callers honor false/no-op return values. This ensures live synchronization cannot report a successful local scenario mutation or alter any local history/context.

## Phone and sidebar rendering

Update `PhoneScreen` and `ConversationView` so `liveSessionActive && liveProjection` selects the projection's `timeline` instead of local `history`. The normal branch remains unchanged. Add `src/components/phone/LiveStateIndicator.tsx`, rendered above the scrollable conversation, using the same projection selector as the sidebar. It shows the local flow label for `currentNodeId` when available, otherwise the stable ID or `Unavailable`, session status, pending input type when present, and the most recent inbound/outbound/provider activity time and sanitized preview. It also labels stale/error sync state. No typing indicator, delay, input bubble, or handset/open/read state is added.

Add a `readOnly` prop to `MessageRenderer` and thread it through all callback-bearing renderers. In live mode it forces `interactive=false`, omits trailing local actions and floating choice callbacks, and suppresses `ListSheet`, boarding-pass preview, external-action modal, and `Toast` mounting from `PhoneScreen`. `VideoMessage` and `DocumentMessage` specifically render non-button previews in read-only mode instead of their unconditional toast buttons. `Carousel` hides its arrow callback buttons in read-only mode (horizontal scrolling remains a passive browser gesture); `SuggestedReplies`, `SuggestedActions`, `RichCard`, `LocationMessage`, `BoardingPass`, `PaymentRequestMessage`, `CalendarEventMessage`, `ProductCatalogMessage`, `WhatsappFlowMessage`, and OTP/list paths receive the explicit read-only/interactive value and cannot call store handlers. Existing normal-mode handlers and visuals remain unchanged. A live content click must never send a message, advance a node, open a simulator overlay, or create a toast.

The composer keeps its existing live lock and restart control. Its live branch is selected before local input lookup, so it cannot submit local text; restart remains the only phone control and uses the synchronized restart response. Extend `LiveRcsControls` to show current node label/ID, status, latest inbound, latest outbound, provider state, stale state, and activity time from `liveProjection`; it does not independently reconstruct events. `LiveDiagnosticsPage` continues to show the explicit sanitized diagnostics DTO for troubleshooting rather than raw provider data.

## Responses to design review findings

1. **Initial delivery failures are not recoverable — addressed.** Creation/restart persist before and during sends, typed `LiveDeliveryError` includes the safe session ID and snapshot, and `app.js` returns the explicit 502 recovery envelope. The client installs that snapshot, activates/retains live mode, marks the view stale/error, and polls the session.
2. **Read-only rendering misses media/document side effects — addressed.** `readOnly` is an explicit renderer prop, is threaded through every callback-bearing message path, and `VideoMessage`/`DocumentMessage` use non-button content in live mode. Phone overlays/toasts are not mounted, and component tests assert no simulator handler or toast runs.
3. **Diagnostics redaction is underspecified — addressed.** Diagnostics now use a concrete allowlist DTO with bounded fields. Provider IDs, bodies, routing fields, variables, correlation/processed IDs, webhook payloads, credentials, and URLs are omitted; tests assert actual private values do not occur in serialized presenter or diagnostics JSON.
4. **Variable-key filtering misses interpolated secrets — addressed.** `metadata.livePublicVariables` is the explicit visibility boundary, private values become `[hidden]`, sensitive-name and credential-pattern denylists apply even to listed values, and user text/activity uses the same redactor. A `verificationCode` fixture is required in tests.
5. **Route error mapping is not implementable — addressed.** Typed service error classes, fixed public codes/messages, deterministic status mapping, and the stable `{error:{code,message}}` schema are defined. Provider details stay in bounded internal diagnostics; webhook mappings are specified separately.
6. **Live-mode mutation locking is incomplete — addressed.** Guards occur before any parse, validation, persistence, or state write and cover scenario loading/import/edit/delete, flow/channel/platform/start-node/variable/brand setters, compare mode, and all interaction handlers. Tests enumerate the public mutators.
7. **Reply actions without targets lack semantics — addressed by rejection.** Server and client Live RCS compilation reject every routable choice/reply/input without `next` as `LIVE_FLOW_INVALID`; only `open_url` is non-routing and it is display-only in the mirror. No ambiguous terminal/no-transition event is introduced.
8. **Activity and label bounds are unspecified — addressed.** Exact limits are defined for previews (240), labels (160), keys (64), values (256), timeline size (500), and existing content limits; truncation is Unicode-safe and boundary-tested.
